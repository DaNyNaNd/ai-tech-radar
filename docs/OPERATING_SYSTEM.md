# AI Tech Radar Operating System

This repo is not here to help you read more. It is here to help you make better decisions and try small workflow improvements without spiraling into tool tourism.

## The hard limitations

- This feed is a filter, not truth.
- The output is only as good as the sources you select.
- “Interesting” does not mean “worth adopting.”
- A recommendation is not validated until you use it on a real task.
- If you keep adding sources, models, and scoring layers before running the experiments, you are procrastinating in a lab coat.

## The rules

1. Read the digest once.
2. Pick only the single suggested experiment.
3. Time-box the experiment to 30 to 90 minutes.
4. Use it on something real, not a toy example, whenever possible.
5. Record the outcome in the experiment log.
6. Either keep, discard, or defer. No vague “maybe later.”

## What counts as success

A daily run is useful only if at least one of these happens:

- You performed the suggested exercise.
- You wrote a short note, blog post, or LinkedIn post about the result.
- You integrated the tool or technique into one actual workflow.
- You made a keep/discard decision with a reason.

If none of those happened, the run was consumption, not learning.

## Grading rubric for an experiment

Score each experiment from 1 to 5 after you try it.

### 1 — Junk
You read about it, touched it briefly, and it did not solve a real problem.

### 2 — Weak signal
Some promise, but friction was high or the value was narrow.

### 3 — Useful but situational
Worth remembering. Not a default.

### 4 — Strong addition
Reduced friction or improved output on a real task. Likely reusable.

### 5 — Keep immediately
Meaningful workflow gain. Should be adopted or revisited quickly.

## Guardrails against self-deception

- Do not spend more time tuning the radar than running the experiments for the week.
- Do not chase more than one tool or paradigm at a time.
- Do not count reading release notes as doing the exercise.
- Do not build infrastructure around a technique you have not validated manually.
- Do not call something valuable until it improves speed, quality, clarity, or reliability in your actual work.

## Weekly review questions

- Which experiment actually changed your workflow?
- Which one looked good in theory and failed in practice?
- What source produced the most useful signals?
- What source is mostly noise and should be cut?
- Did you produce any public artifact from what you tried?

If the answers are vague, the system is drifting and needs to be simplified.
